Window tab → pane splits

Long-pressing a tmux window tab (or right-clicking it with a trackpad) already opens a context menu — Rename, the Move group, Close Window. This adds the four pane splits to the top of that same menu, each one led by a glyph that shows where the new pane lands: the filled half of the window outline is the pane you're about to create.

4 new actions · right / left / down / up native UIMenu — rectangle.*half.filled targets that tab's own active pane Close Window already ships — unchanged

1 · Live demo

Real: long-press a tab (hold ~0.45 s) or right-click it. Hover a split option and the canvas shows a ghost of the result; pick it and the pane grid actually splits — repeatedly, and always from the focused pane, exactly as tmux would. The wire line under the stage prints the command that would go out over the tmux -CC control channel.

2 · Three ways to show the glyphs — decided: A

The reference (macOS Move & Resize) puts four result-glyphs in a single palette row under a header. iPadOS UIMenu rows put the image on the trailing edge — that's the platform convention, and it's what you get for free. Leading glyphs are macOS's convention and would need a custom menu view. Height matters here: the Move group already costs 5 rows, so four more full-height rows makes a very tall menu. A is the one we're building; B and C stay here as the record of what was weighed.

A · Palette + rows ✓ chosen

One palette row, glyph-only, under a “New pane” header — the reference layout. UIMenu.preferredElementSize = .small (iOS 16+) or .displayAsPalette (iOS 17+). Deployment target is 17.0, so both are unconditional.

● 7 elements · ≈362 pt tall · native

B · Rows, native placement

Four ordinary rows appended to the existing sections. Zero new API — just four more UIActions in tabMenuSections. Glyph sits trailing, as every other iPadOS menu does, so it reads as “icon”, not “preview of the result”.

● 11 elements · ≈490 pt tall · native

C · Rows, leading glyphs

The literal macOS look: glyph first, then the label. UIMenu cannot move the image, so this needs a custom menu view — losing the system blur, the lift animation, keyboard navigation and VoiceOver's menu semantics.

● 11 elements · custom view · non-native

Turn on collapse Move into a submenu in the demo above to see A drop to 4 elements (≈190 pt) — palette, Rename, Move ▸, Close. That is the shortest honest menu of the four.

3 · The glyph set

All five are stock SF Symbols — no custom asset, no drawing code. The outline is the window; the solid half is the pane about to be created. Same metaphor Apple uses for window tiling, and it survives at 21 pt in a menu row and at 25 pt in a palette.

Compact (iPhone): nothing to gate

Checked, and it's simpler than “hide the splits on iPhone”: the tab strip does not exist on iPhone. SessionTopBar.styledBar branches on idiom — iPhone renders compactBarCore (back · host switcher · +), and only the regular-width branch builds tabStrip. There is no tab to long-press, so this menu is structurally iPad-only and needs no compact branch, no size-class check and no separate decision. Panes on iPhone stay full-screen: setTmuxGridPresentation(isPhone ? .singlePane : .paneGrid).

Where splits already exist, exactly. Traced every palette.open(…) call site, because “the palette runs on iPad too” is only half true:

SurfaceReachable whenSplits today
Tab context menuiPad, regular width — the only place the tab strip exists none — this change adds 4
Compact switcher iPhone and iPad in narrow Split View / Slide Over — only by tapping the host name in compactBarCore (openCompactSwitcher():12023), never by ⌘K 2-way — but behind a bare .contextMenu on the row (CommandPaletteView.swift:329): long-press only, no ⋯, no chevron, no hint
⌘K quick-switch anywhere — but ContentView.openPalette() passes sessions: only, so tmuxWindows stays empty no tmux rows at all
⌘D / ⌘⇧Danywhere tmux is attached2-way, on the active pane

Caveat that reframes decision 6: the compact menu is real in code but has no affordance — Rename, the four Move items, Tidy, Close and the two splits all hang off an undiscoverable long-press on a palette row. Aligning its glyphs with the tab menu polishes something users are unlikely to find; giving it an affordance is the bigger question. Wired in code; not yet confirmed on a device.

The seam is not “iPad versus iPhone” — it is one iPad, resized. Drag the Split View divider narrow and CompactLayout.isPhone flips on size class, the tab strip disappears, and the same user's split options change from four directions with rectangle.*half.filled to two axes with rectangle.split.2x1 / 1x2. That is decision 6.

6 · Decisions

  1. Treatment. Decided: A — palette + rows, header “New pane”, above Rename.
  2. iPhone / compact. Decided: not applicable — no tab strip exists there, so there is nothing to gate or branch.
  3. Splitting a tab that isn't the focused window. Decided: split, then select that window, so the result is visible.
  4. Labels and disabled states. Decided: “Split Right / Left / Down / Up”, disabled on the existing gates — degraded sync, peer grid authority — same as Move and Close.
  5. The overflow window list. TmuxWindowListPopover keeps its own parallel copy of this menu (menuSections:14353, Move Up/Down rather than Left/Right because it is a vertical list) and shares TmuxWindowInteractionSurface. Without the same palette there, one window has two different menus depending on whether you opened it from the strip or the ▾ list. Default: add it there too. Open.
  6. Shortcuts for left / up. Default: menu-only, no new ShortcutAction cases — ⌘D / ⌘⇧D unchanged. Adding two assignable actions means a new case, label, availability, default chord, wantsPriorityOverSystemBehavior entry, terminal selector and a ShortcutRegistryTests pin apiece, and there is no obvious free chord. Open.
  7. The compact switcher's hidden menu. Rename, Move ×4, Tidy, Close and two axis splits all hang off an undiscoverable long-press on a palette row. Default: leave it untouched here — giving it an affordance is its own piece of work, not part of adding splits. Open.

What ships behind this

  • 4 UIActions in tabMenuSections(window:position:) — SessionView.swift:13045; a palette needs one extra UIMenu with preferredElementSize set in contextMenuInteraction(_:configurationForMenuAtLocation:) (SessionView.swift:13974).
  • TmuxWindowMenuAction gains nothing — it already carries title, systemImage, destructive, disabled and a handler.
  • TmuxController.splitPane(_:axis:) gains a before: Bool (the -b flag) — TmuxControl/TmuxController+PaneCommands.swift:34 — and the wire command .splitTmuxPane carries it across the shared-core ABI, so Android gets the same four directions from one change.
  • The same four actions belong in the overflow window list's row menu (TmuxWindowListPopover) — it mirrors the strip's tabs and would otherwise be the one place a split is missing.
