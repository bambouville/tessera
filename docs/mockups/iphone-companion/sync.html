iPad ↔ iPhone. The server is the sync layer — tmux already holds the session; Apple Continuity carries only a secret-free pointer to it. No vendor cloud, no accounts. Companion to index.html (iPhone mock); design source: P8 in docs/iphone-adaptation-plan.html.

◆server is the sync layer
tmux holds the session; Handoff hands over a pointer, iCloud is never in the session path.
◆invisible until needed
No sync dashboard, no pairing screens. Surfaces: one first-open bootstrap, the system banner, the moment of continuation, one credential step, two Settings groups.
◆attach, don't steal
Continuation joins the same tmux session; the iPad stays attached. Geometry stays server-side (ignore-size).
◆honest labels
"Continue" only when tmux makes it true. Plain SSH / mosh get "reconnect" — same host, fresh shell.
◆secrets never move
No password, no private key, ever — in the descriptor, the stream, or iCloud. Only public data travels.

S1First open — bootstrap from your existing setup

A fresh install of either app offers to inherit the other device's setup: host configs, jump chains, settings & appearance — nearby and device-to-device, or from the user's own iCloud. During setup the new device also creates a default Secure Enclave key, and the origin device can authorize it on existing hosts with one biometric confirm. Both directions below: new iPhone from an existing iPad, then new iPad from an existing iPhone — the surfaces swap devices, the rules don't change.

Transport honesty: the nearby path is a foreground, peer-to-peer transfer over the local network — not Handoff (which only ever carries a session pointer, S2) and not iCloud. Because a bare local-network channel authenticates nobody, the order is mandatory: discover → encrypted channel → code compare (SAS) → Face ID on the origin → transfer. The manifest never moves before the code is confirmed — device names are display-only and are never a trust input. The iCloud row reuses the layer-3 container when that ships; until then it is a grayed option. Trust pins deliberately don't transfer — first connect on the new device still runs informed TOFU (S5) against each descriptor's hostKeyFP, which is also why manifest integrity (the code compare) matters: a poisoned manifest could pre-seed false pins.

S4Locked device — stash & replay

Continuation handlers fire while the lock overlay is up. The continuation stashes, Face ID runs, and the attach replays after unlock — nothing acts behind the lock screen. While Tessera itself is locked it also stops broadcasting (invalidate() on lock), matching the key-use-grant posture. Shown on iPhone; the iPad's lock overlay behaves identically in both directions.

S7One-tap enrollment — authorize this iPhone

Zero-touch key enrollment over Handoff continuation streams: the iPhone sends its public key back to the originating iPad; the iPad — already authenticated — confirms with Face ID and installs it over its live connection (RemoteAuthorizedKeysInstaller, idempotent). If the phone has no key yet, a default Secure Enclave key is generated first, silently. The private key never leaves the Secure Enclave. Direction-agnostic: whichever device holds the authenticated session grants — S3 shows the mirrored pair. Peer binding here is Apple's, not ours: continuation streams only open between devices signed into the same Apple Account (the S9 footnote requirement), mutually authenticated by Apple's identity service — a LAN device outside the account can't be an endpoint. Unlike S1's self-built channel, no code compare is needed; the key fingerprint in the dialog is the end-to-end artifact. This property is transport-load-bearing: if enrollment ever moves off continuation streams, it inherits S1's SAS requirement.

S10Guarantees — what sync will never do

The "never" list is part of the design, not a caveat. Each one is load-bearing for the app's privacy stance.

private keys never move
Secure Enclave keys are non-exportable by construction. Enrollment ships public keys only.
passwords never sync
Stored ThisDeviceOnly by design. Each device asks once, keeps its own copy.
no vendor cloud, no accounts
Handoff is device-to-device; the only cloud ever on the table is the user's own iCloud, opt-in.
no silent connections or grants
Every continuation starts with a user tap; every cross-device grant is a biometric confirm on the origin device; the lock screen always wins.
no in-app nearby list
Discovery is the system surface only. No API exists to enumerate nearby activities — and faking one would need a server.
no geometry theft
Attaching from the phone never resizes the server-side grid, splits, or zoom (ignore-size; no window-size latest).
no unverified peers
Nearby transfers bind with a code compare before anything moves; Handoff streams are Apple-Account-authenticated; a device name is never a trust input.
build order (matches P8): layer 1 — broadcast + continue both directions + informed TOFU (S2–S6) · layer 2 — enrollment, first-open bootstrap (nearby path), ledger (S1, S7, S8) · layer 3 — iCloud (S1 restore row + S9 frames 2–3, separate proposal).
