Files panel improvements

Four additions to the Remote Files panel and terminal: ① filter/search in the toolbar, ② tap-to-edit path bar for direct navigation, ③ Quick Look from selected terminal text (right-click / selection menu), and ④ quick-open by path. All four ride the existing per-host file bridge (SFTP side channel), so they behave identically on SSH, SSH+tmux, mosh, and mosh+tmux.

1 · Toolbar search — filter the listing without leaving the tree

A search button joins the toolbar (right side, after the spacer, next to the new quick-open button — both monochrome glyphs, same 28×24 hit target as the existing tools). Tapping it slides a filter field in under the toolbar and focuses it. Typing filters the loaded rows live — current directory plus any expanded subfolders — with match highlighting. It's a filter, not a host-wide find: instant, offline, no extra SFTP round-trips.

1Two new toolbar buttons. Search (magnifyingglass) and quick-open (arrow.right.doc.on.clipboard-style glyph, §4) sit right-aligned after the spacer — the left group stays the five existing action tools. Same toolButton factory, same accessibility labels.
2Filter row. Appears under the toolbar (28pt, accent border while focused), auto-focuses the keyboard, and filters controller.rows case-insensitively as you type. Matches highlight the matched range in accent; rows from expanded subfolders flatten in with a dim parent-path tag. × or esc clears and collapses; the search button shows accent-tinted while a filter is live so a filtered (shorter) list is never mistaken for the directory content. Sets textEntryActive while focused (same as the rename/new-folder alerts) so the terminal doesn't reclaim the keyboard.

Not in v1: recursive host-wide search (would need find execution or SFTP walking — a different, slower feature; the filter's instant feedback is the 90% case). Directories whose children match but that aren't expanded don't auto-expand in v1 — the filter works on what's loaded.

2 · Editable path bar — tap the crumbs, type a destination

The breadcrumb strip already navigates up; tapping its empty area (or long-pressing anywhere on it) now flips the bar into a text field pre-filled with the current absolute path, fully selected — one keystroke replaces it, arrow keys edit it. Paste works. ⏎ navigates, esc reverts to crumbs. Prefix completion is built in: each path segment autocompletes from the parent directory's listing as you type. The follow toggle keeps its slot; a manual navigation drops follow to manual browse exactly like tapping a crumb does.

1Edit mode. The crumbs swap for a TextField (mono 10.5, autocorrect/capitalization off, accent hairline). Pre-filled with the absolute path so copying the current location out is also free. ~ and relative input resolve against $HOME / current directory before navigate(to:). Nonexistent or non-directory path → the existing error banner (“No such directory: …”), field stays for correction. While editing, textEntryActive is set — terminal keeps its hands off the keyboard.
2Inline completion (required). The segment after the last / prefix-filters the parent directory's entries — one listDirectory over the bridge, served from the per-directory cache the browser already fills, ~150 ms debounce for cold parents. Up to 6 matches drop down under the bar, directories first, matched prefix in accent. ↑↓ move the highlight, tab accepts the highlighted entry (appending / for a directory so you keep typing deeper), ⏎ accepts and navigates. esc closes the dropdown first, then exits edit mode. No matches → no dropdown; the typed path is still submittable as-is. Touch: tapping a suggestion row = tab-accept.

3 · Quick Look from terminal selection — select a path, right-click, preview

Yes — feasible without touching text rendering. SwiftTerm's selection already flows through iOS's edit-menu plumbing (UIEditMenuInteraction); we add a Quick Look action that appears whenever the selected text resolves to a plausible remote path. Trackpad right-click on a selection shows the same menu (iPadOS presents it as a vertical context menu at the pointer); finger selection shows the horizontal callout bar with the same items. The file streams over the file bridge into the existing QuickLookPresenter — the terminal transport is never involved, so it works identically under mosh and tmux.

1Menu placement. “Quick Look” (+ optional “Reveal in Files Panel”) joins Copy/Select All in the terminal's edit menu — right-click vertical menu with a trackpad, horizontal callout with touch. The items only appear when the selection looks like a path (single line after trimming, no spaces-heavy prose, contains / or a known file extension) — everyday copy flows never see extra clutter.
2Resolution. Trim whitespace/quotes/trailing punctuation, strip :line:col suffixes (compiler output), expand ~, resolve relative paths against the session's cwd (same OSC 7 / tmux pane_current_path signal the follow mode uses). Then stat over the file bridge: file → stream + QuickLookPresenter; directory → “Reveal in Files Panel” opens the panel there. The stat runs when the menu action fires, not during menu build — menu construction must stay synchronous and fast.
3Miss case. If the stat fails (deleted file, cwd signal stale, prose that looked like a path), a transient toast reports it — same pill style as the terminal drop-target failure toast. No modal, no panel state change.

Cwd caveat: without shell integration on a plain-SSH/mosh host, relative paths can't be resolved — absolute and ~ paths still work, and a relative-path miss suggests “install shell integration” in the toast. Size guard: files over ~50 MB confirm before streaming (mobile data).

4 · Quick open — preview any file by typing its path

The second new toolbar button (next to search). Tap → a small anchored popover with a single mono path field. ⏎ resolves the path over the bridge: file → Quick Look, directory → panel navigates there. It's the keyboard-first sibling of §3: same resolver, same preview path, no selection needed. Recent quick-opens (last 5, per host) sit one tap away below the field.

quick-open popover, anchored on its toolbar button
  • One resolver, three entry points. §2 (path bar), §3 (selection), and §4 (quick open) all call the same RemotePathResolver: normalize → expand ~ → resolve relative against cwd → stat → route (file = preview, dir = navigate). Build once, wire three UIs.
  • Same completion as the path bar. The quick-open field reuses §2's suggestion dropdown verbatim (same matcher, same tab/↑↓/⏎ keys) — one component, two hosts.
  • Why a popover and not the path bar? The path bar edits where the panel is (a directory); quick open answers “show me this file now” without moving the panel. Different intent, different verb — and the popover keeps the panel's browsing state untouched.
  • Keyboard: ⌘⇧O proposed (⌘O is claimed by many document apps but available in-app; verify against the iPadOS system HUD before shipping — same drill as ⌘⇧E for the panel toggle).
  • Recents persist per host key in the panel's existing per-session state (not SwiftData — ephemeral cache, losing them on relaunch is fine in v1).
  • Errors reuse the panel error banner (“Not found: …”, “Permission denied: …”), field stays for correction.
