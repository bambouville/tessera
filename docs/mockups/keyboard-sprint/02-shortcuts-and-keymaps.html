custom shortcuts & keymap remapping

One surface, two features. The read-only shortcut list in settings → keyboard & input becomes an editable keymap, and the same editor is where a user defines their own shortcuts — a chord, a bar chip, or both, sending text or keys to the remote. They share a table, a recorder, and a conflict model, so building them apart would mean building the recorder twice.

Today KeyboardSettingsView ends with a static ShortcutLegend: six groups of hard-coded strings, iPad-only, read-only. It's replaced by a summary card that states what's bound and opens the editor. the one hard rule: every app shortcut contains ⌘

The terminal owns bare keys and ⌃-combos — that's the entire point of the product. A user who binds "toggle files panel" to loses ^E (end-of-line) in every shell forever, and will report it as a bug. So the recorder rejects any chord without ⌘, with that sentence as the reason. ⌥ alone is rejected for the same reason (⌥ is meta/ESC-prefix).

This isn't a limitation to apologize for — it's what keeps remapping from silently breaking the shell. The "sent to shell" category exists to say so out loud, in the same table, instead of leaving users to discover it.

rows that can't be freely remapped, and why

  • ⌘1–⌘9 is a nine-key block sharing one selector — the editor remaps the modifier (⌘ → ⌃⌘), never individual digits.
  • esc closes the find bar and dismisses overlays; it's the platform dismiss gesture, fixed.
  • ⌃Tab and ⌘+arrows can be typed but never captured — iPadOS's focus engine takes Tab-family keys, and SwiftTerm's UITextInput first responder eats arrows before an ancestor's keyCommands is consulted. Both are already documented in TesseraTerminalView.swift; the recorder must name them rather than appear to hang.
  • ⌘W, ⌘H, ⌘Space, ⌘Tab — claimed by iPadOS/Stage Manager before the app sees them.

The recorder cannot be a UIKeyCommand list. Key commands only fire for chords you registered in advance — the recorder must observe arbitrary presses, so it uses pressesBegan/pressesEnded on a focused capture view with the terminal resigned as first responder. That's also what makes the "can't be captured" state honest: a chord the focus engine swallows never reaches pressesBegan either, so the recorder detects "modifier held, no key ever arrived" and says so instead of waiting forever.

why not reuse the swipe pad's macro language?

MacroEncoder looks like the obvious fit, and it isn't. It strips every space (git status↵ → gitstatus) and matches the bare words tab / esc anywhere they end at a boundary — so crontab -l encodes as cron<TAB>-l. Fine for the 1–3 character agent replies it was written for; wrong for arbitrary command text.

Hence the token field: literal text stays literal, special keys are pills, and there is no grammar to get wrong. Stored as a typed array — [.text("git status"), .key(.return)] — not a string that needs re-parsing.

The swipe pad keeps its spec language untouched. Worth a separate ticket: the same two quirks are live for anyone writing swipe-pad macros today.

icon vs text on the chip — yes, with one adjustment

You're right that a pictogram beats truncated text at 44pt: deploy is six characters of 11pt mono, ⟳ is one shape you find by muscle memory. So icon is the default label mode, text the alternative.

The adjustment: default to SF Symbols, not emoji. The bar is chrome, and the app's rule is monochrome glyphs — a 🚀 would be the only saturated color object in the entire session UI, and five of them turn the bar into a sticker sheet. SF Symbols give you the same memorability, tint with the theme and the armed-modifier accent, and stay legible at 44pt on both devices.

Emoji stay available behind an explicit emoji… button, because it's the user's own bar and the symbol library won't have everything. Shipping it as the default is what I'd avoid; offering it costs nothing — the field takes any single character either way.

Required either way: an icon chip has no text, so the shortcut's name becomes its VoiceOver label. That's already why the name field is mandatory and why it's the first field in the form rather than an afterthought.

05

iPhone, and iPad without a keyboard

You asked for keymap remapping on iPad. The honest gate isn't the device though — it's whether a hardware keyboard is attached. An iPad in portrait with no Magic Keyboard has exactly the same problem an iPhone does, and an iPhone with a Magic Keyboard has none of it. So: chord editing is gated on GCKeyboard.coalesced != nil, and custom shortcuts ship everywhere.

What iPhone gets: the full custom-shortcut editor (name, action, scope, chip), the chip on the accessory bar, the swipe-pad petal, and a read-only view of every app shortcut with its chord — which is useful precisely because the same person will pick up their iPad later. Chords they set on iPad display here and fire here the moment a keyboard is attached, because the binding is data, not a per-device UI state.
What it doesn't get: the recorder, when no keyboard is connected — with the reason stated in place rather than the rows silently doing nothing on tap. The keymap table also collapses from a three-column table to a pushed list, matching how every other settings section already behaves on phone.
Both devices: the keymap override delta and the custom-shortcut list travel on the existing continuity channel alongside hosts and prefs. A shortcut is worth having on exactly the device you didn't define it on.
06

what this costs to build

piecesizenotes
Keyboard/ShortcutAction.swiftnew The action catalog: one case per bindable app action, each with a title, group, default chord, and availability predicate (tmux attached / multi-pane / iPad-only). Today those facts are scattered across keyCommands, canPerformAction, and a hard-coded legend — this makes the legend a projection of the registry instead of a copy of it.
Keyboard/KeyBinding.swiftnew Chord (modifier set + key) ↔ UIKeyCommand, plus validation: requires ⌘, reserved list, uncapturable list. Pure and fully unit-testable — the conflict matrix belongs in tests, not in a QA pass.
Keyboard/ShortcutStore.swiftnew Overrides + custom shortcuts as a JSON delta in UserDefaults, merged over defaults on load — the exact model SwipePadProfileStore already uses. Not SwiftData: adding a column to a @Model that owns a [String] crashes iOS 26 lightweight migration, and PersistedHost is one.
TesseraTerminalView.swiftmedium keyCommands stops being a literal list and becomes a map over the registry; canPerformAction keeps the availability gates. ~34 hard-coded UIKeyCommand(input:modifierFlags:) calls collapse. The doc comments explaining why each chord was chosen must survive onto the registry entries — they're the record of what's already been tried and failed.
ContentView.swift · HostDetailView.swift · AgentCenterPage.swiftsmall Six SwiftUI .keyboardShortcut() call sites read their chord from the store instead of a literal.
Keyboard/AccessoryChip.swiftsmall Chips gain a custom case carrying a label kind — .symbol(String) (SF Symbol name, the default), .text(String), or .character(Character) for an emoji. accessoryBarKeys is [String] and decoding runs through compactMap(AccessoryChip.init(rawValue:)) — so a "custom:<uuid>" id is silently dropped by any build that doesn't understand it. Forward and backward compatible for free; worth an explicit test so it stays that way. The chip view branches on label kind: Image(systemName:) vs Text, with the shortcut's name as the accessibility label in every case.
Settings/ShortcutsEditorView.swiftnew, large The sheet in §02–04: table, rail, recorder, custom editor. The recorder is the only genuinely tricky part (first-responder handoff + pressesBegan).
Settings/KeyboardSettingsView.swiftsmall ShortcutLegend deleted; summary card in its place. Stops being iPad-gated.
SwipePad/MacroEncoder.swiftuntouched Deliberately. Custom shortcuts use their own token model (§04) rather than inheriting the space-stripping and bare-word-matching quirks.
Cross-transport: app chords are intercepted before the wire, so they behave the same on all four transports. Custom send-text/send-keys shortcuts do hit the wire and need checking on each: plain SSH and mosh take the bytes directly; under tmux -CC they must go through the pane's input path, not the control channel; and a chip that ends in ↵ while a pane is zoomed or an alt-screen app is running behaves like any other typed input. One integration case per transport, asserting the same bytes arrive.
The regression that worries me: keyCommands is rebuilt on every responder query, and the array's order plus wantsPriorityOverSystemBehavior currently decide which of two overlapping chords wins. Driving it from a user-editable store makes that ordering a user-visible variable. The registry needs a deterministic sort and a test that the shipped defaults produce the same effective bindings as today's literal list — that's the one place this refactor could quietly change behavior for users who never open the editor.
